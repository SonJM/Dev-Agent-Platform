## 목적
서버의 Dev Agent가 공유 PostgreSQL에 **호스트 포트 공개 없이** 붙는다. DB 컨테이너와 그 compose, 다른 서비스는 손대지 않는다.

## 근거
- 결정: `OI-18`(2026-11-25 — 방법 (c) 기동 때 조회) ([00-INDEX](../00-INDEX.md)), 설계 [02 §4.2 D-3](../02-architecture.md), 배포 [04 §9](../04-project-structure.md)
- 제약: `CON-06`(공유 인스턴스에서 지킬 것) ([01](../01-requirements.md))
- 선행 산출물: T-003의 `deploy/`([설명서](./results/T-003-서버-실행-구성.md))
- 코드 확인(PM, 2026-11-25)
  - `boot/Bootstrap.val()`은 **프로세스 환경변수를 먼저** 보고 없을 때만 `.env` 값을 쓴다. `DB_URL`이 둘 다 비면 내장 DB를 띄운다(`Bootstrap.prepare`).
  - Spring 쪽은 `application.yml`의 `${DB_URL:}`이고 `.env`는 `spring-dotenv`가 읽는다. 환경변수와 `.env`에 `DB_URL`이 **둘 다 있을 때의 Spring 쪽 우선순위는 확인하지 않았다** — 그래서 이 설계는 서버 `.env`에 `DB_URL`을 두지 않게 한다(아래 범위 4).
  - 외부 DB에 붙지 못하면 `Bootstrap`은 스키마 확인만 건너뛰고, 뒤이은 Spring 접속 실패로 앱이 0이 아닌 코드로 끝난다(내장 DB로 넘어가지 않는다).
- 서버 사실(메인 세션 읽기 전용 확인, 2026-11-25 — 값은 저장소에 적지 않는다): DB 컨테이너는 호스트 포트를 공개하지 않고 bridge 네트워크 하나에 붙어 있으며 고정 IP 설정이 없다. 호스트에서 컨테이너 주소의 5432로 TCP 연결이 된다. `pg_hba`는 루프백 밖 접속에 `scram-sha-256`을 요구한다. 서비스 계정은 sudo 없이 docker 명령을 쓸 수 있다.

## 관련 코드 경로
- 신규: `deploy/bin/start-server.sh`, `deploy/smoke/start-server-check.sh`
- 수정: `deploy/systemd/dev-agent.service`, `deploy/env.server.example`, `deploy/README.md`
- 참고(고치지 않음): `src/main/java/.../boot/Bootstrap.java`, `src/main/resources/application.yml`, `deploy/smoke/server-smoke.sh`

## 범위
1. **`deploy/bin/start-server.sh`** (bash, LF, `set -eu`) — unit의 `ExecStart`가 이 스크립트에 java 명령을 인자로 넘긴다.
   - 입력(환경변수, unit이 준다): `DB_CONTAINER`(필수), `DB_NAME`(필수), `DB_PORT`(기본 5432), `DB_NETWORK`(선택 — 컨테이너가 네트워크 여러 개에 붙어 있을 때 고를 이름), `DB_WAIT_SEC`(기본 60).
   - `docker inspect`로 컨테이너가 실행 중인지와 주소를 얻는다. 얻은 값이 **IPv4 하나**인지 형식을 확인한다(네트워크가 여러 개인데 `DB_NETWORK`가 없어 값이 이어 붙은 경우도 여기서 걸린다).
   - 주소를 못 얻으면 `DB_WAIT_SEC` 동안 2초 간격으로 다시 시도한다(부팅 직후 docker는 떴지만 컨테이너가 아직 안 뜬 경우). 끝내 못 얻으면 **이유 한 줄을 stderr에 쓰고 0·10이 아닌 코드로 끝낸다. java를 실행하지 않는다** — `DB_URL` 없이 java가 뜨면 앱이 내장 DB로 조용히 떠 버린다.
     - 바로 실패하지 않고 기다리는 이유: unit은 3분 안에 5회 실패하면 멈춘다(`StartLimitBurst`). 5초 간격으로 즉시 실패하면 부팅 때 30초 만에 포기한다. 60초 대기면 5회에 3분을 넘겨 계속 재시도한다. 이 계산을 unit 주석에 적는다.
   - 작업 디렉터리의 `.env`에 주석이 아닌 `DB_URL=` 줄이 있으면 "서버에서는 `.env`에 `DB_URL`을 두지 않는다"는 안내와 함께 실패한다(두 값이 어긋나 `Bootstrap`과 Spring이 서로 다른 DB를 보는 일을 막는다).
   - `DB_URL=jdbc:postgresql://<조회한 주소>:<DB_PORT>/<DB_NAME>`을 `export`하고 `exec "$@"`로 넘긴다(java가 주 프로세스가 되어 종료 코드 10·0 규약과 SIGTERM 처리가 그대로다).
   - 비밀번호를 다루지 않는다(`DB_USERNAME`·`DB_PASSWORD`는 앱이 `.env`에서 읽는다). 조회한 주소는 로그에 한 줄 남겨도 된다(journal에만 남는다).
2. **`deploy/systemd/dev-agent.service`**: `Environment=DB_CONTAINER=<DB_CONTAINER>`·`Environment=DB_NAME=<DB_NAME>`(자리표시자), `ExecStart=<APP_HOME>/start-server.sh <JAVA_HOME>/bin/java …`(java 인자는 현행 유지). 머리 주석의 자리표시자 목록과 "DB가 아직 안 떴으면…" 설명을 새 동작에 맞춘다. `Restart`·`RestartForceExitStatus`·`SuccessExitStatus`·`After=docker.service`는 그대로.
3. **`deploy/README.md`**: 구성 요약(7행), 자리표시자 표, §2(포트 공개 절차 → "포트를 공개하지 않는다. 기동 때 주소를 조회한다"와 설치 전 확인 명령: 서비스 계정으로 `docker inspect`가 되는지, 호스트에서 컨테이너 5432에 연결되는지), §4(`.env`에 `DB_URL`을 적지 않는다), §6(스크립트 복사·실행 권한, 늘어난 자리표시자 치환), §8 확인 항목(호스트에 5432 리슨이 **없다**, 앱이 외부 DB로 떴다 — 플랫폼 탭 「시스템」의 DB가 "외부"), §11 문제 해결(DB 컨테이너를 다시 만들어 주소가 바뀌면 `systemctl restart dev-agent`, 스크립트 실패 메시지별 조치). "브리지 주소는 권하지 않는다"는 옛 문장은 지우고, 주소가 바뀌는 경우의 동작을 사실대로 적는다.
4. **`deploy/env.server.example`**: `DB_URL` 줄을 없애고 "서버에서는 unit의 시작 스크립트가 `DB_URL`을 만든다. 여기 적으면 시작이 거부된다"는 주석으로 바꾼다. `DB_USERNAME`·`DB_PASSWORD`는 유지.
5. **`deploy/smoke/start-server-check.sh`**: 서버 없이 스크립트 동작을 확인한다. 임시 디렉터리에 가짜 `docker` 실행 파일을 만들어 `PATH` 앞에 두고 아래를 확인한 뒤 전부 통과하면 마지막 줄에 `CHECK PASS`, 하나라도 어긋나면 `CHECK FAIL`과 0이 아닌 코드.
   - 정상: 가짜 docker가 주소 하나를 주면 넘겨받은 명령이 실행되고 그 환경의 `DB_URL`이 기대한 값이다.
   - 실패 4종: 컨테이너 없음(docker 실패) / 중지 상태(빈 주소) / 값이 IPv4 하나가 아님 / `.env`에 `DB_URL=` 있음 → 0·10이 아닌 코드이고 **넘겨받은 명령이 실행되지 않았다**. 이때 `DB_WAIT_SEC`는 짧게(예 2) 준다.
   - 필수 환경변수(`DB_CONTAINER`·`DB_NAME`) 누락 → 실패.
   - 시험용 주소는 문서용 대역(`192.0.2.x`)을 쓴다.
