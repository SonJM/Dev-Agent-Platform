## 범위
- `deploy/systemd/dev-agent.service`(틀): `User=<SERVICE_USER>`(CLI 로그인이 돼 있는 기존 일반 계정, root 아님), `WorkingDirectory=<앱 홈>`, `Environment=PATH=…`와 `JAVA_HOME=…`(systemd는 로그인 셸 PATH를 쓰지 않는다 — JDK·`~/.local/bin`·node 경로를 자리표시자로), `Environment=DEV_AGENT_RUN_MODE=systemd`, `ExecStart`의 java는 절대 경로 자리표시자, `Restart=on-failure`(종료 코드 0은 재기동하지 않음, 10은 재기동), 재기동 간격·횟수 제한, docker 뒤에 시작, 부팅 시 자동 시작. 실제 계정 이름·경로 값을 저장소에 쓰지 않는다.
- `deploy/sql/create-db.sql`: 공유 PostgreSQL 인스턴스에 **전용 role(LOGIN, 그 외 권한 없음 — SUPERUSER·CREATEDB·CREATEROLE 아님)과 그 role이 소유한 전용 DB**를 만드는 SQL. 이름과 비밀번호는 자리표시자(psql 변수). 다른 DB·role을 건드리는 문장을 넣지 않는다. 전용 DB에 대한 `PUBLIC`의 접속 권한을 거두는 문장을 포함한다. 테이블은 만들지 않는다(앱 첫 기동이 만든다).
- `deploy/env.server.example`: 서버에서 필요한 키 이름과 설명만(값 없음). `ACCESS_ALLOWED_ORIGINS`(형태 예시 `https://<MagicDNS 이름>:8443`), `DB_URL`(형태 예시 `jdbc:postgresql://127.0.0.1:5432/<전용 DB>`)·`DB_USERNAME`·`DB_PASSWORD`(자리표시자), `GITLAB_WORK_DIR`(작업 디렉터리는 앱 홈 밖), `PREVIEW_ENABLED=false`, `MAINTAIN_ENABLED=false`(OI-14 미정 — 기본 끔) 포함. 숫자형·기본값 있는 키는 빈 값으로 두지 않고 주석으로 둔다(`CLAUDE.md`).
- `deploy/README.md`(절차서, 한국어)
  1. 사전 확인: **로그인 셸에서** java·claude·git 경로와 버전, CLI 로그인 상태. 서버의 도구는 로그인 셸 PATH에서만 보인다는 점과, 그 경로를 unit의 `PATH`·`JAVA_HOME`에 옮겨 적는 방법.
  2. **사용자가 할 일 — 공유 PostgreSQL 접속 경로(OI-18)**: 그 DB 컨테이너는 호스트 포트를 공개하지 않는다. 그 compose에 `127.0.0.1:5432:5432` 공개를 더하고 컨테이너를 다시 만든다. 이때 그 DB를 쓰는 다른 서비스들이 순간 끊긴다는 점, 서비스 정리 때 함께 하라는 점, 브리지 IP 접속을 권하지 않는 이유, 적용 뒤 `ss -ltn`으로 `127.0.0.1:5432`만 열렸는지 보는 방법을 적는다. 이 절차서와 저장소는 그 compose 파일을 고치지 않는다.
  3. 전용 DB·role 만들기: `create-db.sql` 실행 방법(서버에 psql이 없으므로 DB 컨테이너 안의 psql로 실행하는 형태 — 컨테이너 이름은 자리표시자), 비밀번호 정하기.
  4. 앱 홈·`.env`(권한 600).
  5. jar 올리기(개발 PC에서 만든 jar. 서버 빌드는 Java 17 toolchain 필요).
  6. unit 설치·시작·로그 보기.
  7. `tailscale serve`: HTTPS **8443** → `127.0.0.1:8777`, 끄는 방법, tailnet HTTPS 인증서가 꺼져 있을 때의 증상과 켜는 곳.
  8. 확인 항목(아래).
  9. 갱신(새 jar)·되돌리기.
  10. 전용 DB만 대상으로 하는 수동 백업(`pg_dump`)과 복원.
  11. 문제 해결.
- 확인 항목에 반드시 포함
  - 8777이 `127.0.0.1`에만 열려 있다. DB 포트가 `127.0.0.1`에만 열려 있다.
  - **공유 인스턴스 보호**: 첫 기동 뒤 전용 DB에만 테이블이 생겼고 다른 DB의 테이블 수·role 목록이 그대로다. 전용 role로 다른 DB에 접속되지 않는다. Dev Agent의 연결 수가 5 이하다(`pg_stat_activity`). 코드 조사 결과(`Bootstrap`이 접속한 DB의 `public.bot_setting`만 보고 DROP을 뺀 `schema.sql`을 실행, 매퍼 DDL은 `CREATE … IF NOT EXISTS`·`ALTER TABLE`뿐)를 절차서에 근거로 적고, 이 지시서에서 **다시 코드로 확인**해 다르면 보고한다.
  - tailnet PC·모바일에서 화면·실시간 로그·리서치 이미지 첨부 동작, tailnet 밖에서 접근 불가.
  - **접근 제어(T-002) 서버 확인**: `ACCESS_ALLOWED_ORIGINS`를 채운 상태에서 serve 주소로 연 화면의 상태 변경(스킬 등록·삭제 등)·SSE·파일 올리기가 403 없이 동작하고, 다른 Origin의 POST는 403. 그리고 **`tailscale serve` 뒤에서 앱이 받는 `Host`·`Origin` 헤더 값**을 확인하는 방법(앱 코드 변경 없이 — 예: 임시 수신 서버나 기존 로그 이용)과 결과를 적을 칸. 이 값은 OI-21 결정 자료다. Host 검사 자체는 이 작업 범위 밖.
  - 화면의 재시작·종료 동작, 서버 재부팅 뒤 자동 기동(DB 컨테이너보다 먼저 떠도 재시도로 붙는지).
  - systemd 아래에서 에이전트 1회 실행(CLI가 git·빌드 도구를 찾는지, 자격증명 갱신).
- **확인되지 않은 것은 "확인 필요"로 표시**하고 확인 방법을 적는다. 추측을 사실처럼 쓰지 않는다.
- unit 문법 확인(`systemd-analyze verify`)은 개발 PC에서 할 수 없다 — 절차서의 설치 단계에 사용자가 실행할 명령으로 넣는다.
