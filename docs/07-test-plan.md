## 1. 범위

### 1.1 대상
- 전환으로 바뀌는 것: Linux 기동, 접근 제어, 메신저 수신 경로, GitHub 연동, Telegram 어댑터, SPA.
- 전환 중 깨지면 안 되는 기존 화면 흐름(FR-6xx)의 회귀.

### 1.2 제외
- Claude CLI를 실제로 호출하는 흐름(이슈 분석·수정, 리서치 답변)의 자동 테스트 — 구독 토큰을 쓰고 결과가 비결정적이다. 사용자가 서버에서 수동으로 확인한다.
- 실제 GitHub·Telegram을 상대하는 자동 테스트 — 토큰이 필요하다. HTTP 응답을 흉내 낸 단위 테스트로 대신하고, 실제 연동은 사용자가 수동 확인한다.
- 서버에서의 `tailscale serve` 동작(FR-103) — 사용자가 절차서의 확인 항목으로 본다.

## 2. 전략

| 유형 | 대상 | 도구 | 위치 | 기준 |
|---|---|---|---|---|
| Unit | 순수 함수, 필터, 라우터, 클라이언트(요청 조립·응답 해석) | JUnit 5 (Spring 컨텍스트 없음, 현행 방식). HTTP는 `MockRestServiceServer` 또는 가짜 구현 | `src/test/java` | 새로 쓰는 코드 80% 이상 |
| Integration | Linux 기동 | 셸 스크립트 — SSH로 서버에서 격리 실행(격리 디렉터리·다른 포트·내장 DB, 끝나면 정리) | `deploy/smoke/server-smoke.sh` | TC-001 통과 |
| E2E | 핵심 화면 흐름 | Playwright | `e2e/` | §8 핵심 TC 묶음 |
| 수동 | 서버 접근, 실제 GitHub·Telegram, 에이전트 실행 | `deploy/README.md`의 확인 항목 | — | 단계 종료 때 사용자 확인 |

기존 저장소에는 Spring 컨텍스트를 띄우는 테스트가 없다. 이번 전환에서 통합 테스트 기반(Testcontainers 등)을 새로 들이지 않는다 — 기동 확인은 TC-001과 E2E가 맡는다.

| 서버(정식) | 사용자가 `deploy/README.md`의 확인 항목으로 수동 확인 | 공유 PostgreSQL의 전용 DB |

### 데이터 규모 가정

| 대상 | 가정 | 출처 |
|---|---|---|
| 이슈 세션 | 누적 수백 건, 동시 진행 2건 | 사용자 1명 · `concurrency` 기본값 |
| 세션당 이벤트(`issue_event`) | 수천 행 | 개발 단계 최대 600턴 설정 |
| Diff | 파일 71개 · 2,485줄(실측 사례) | `CLAUDE.md` |
| 리서치 스레드 | 수백 건, 결과 문서 최대 60,000자 | `research.max-result-chars` |
| 스킬 / 루틴 / MCP | 각 수십 건. 루틴은 앱 상한 50건 | 사용자 추정 · 루틴 상한은 T-004 확인 |

QA seed(`e2e/seed/seed.ts`)는 스킬 60건(가정의 2배), 루틴 30건(상한 50이라 2배를 넣을 수 없다 — 여유 20을 남김, 실행되지 않게 비활성), 경계값 4행을 넣는다(T-004).
