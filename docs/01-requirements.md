# 01. 요구사항 정의서

> Dev Agent — 개인 개발 서버용 에이전트 운용 플랫폼으로의 전환(2.0)
> 버전 0.4 · 2026-11-25 · 상태: Draft
> 확정 기술 스택은 [00-INDEX](./00-INDEX.md) 참조

---

## 1. 배경 및 목적

### 1.1 현황
- 1.12.0은 사내에서 쓰던 로컬 플랫폼이다: Windows PC에서 돌고, `127.0.0.1`에만 열리며 인증이 없다.
- 사내 전용 기능(메신저 방 수집·정기 요약·멘션 초안/자동응답, 사내 문서 RAG)과 GitLab 연동, 사내 브랜치 컨벤션(develop 고정, 일감번호)이 들어 있다.
- 메신저 명령(`@AI …`)과 확인 대기 답변은 **방 수집 경로**(`CollectService` → `chat_message` → `MentionService.handleCommand`, `IssueAgentService.pollReplies`)로만 들어온다. 수집을 지우면 수신 경로가 사라진다.
- Linux 실행은 검증된 적이 없다. 트레이·자동 실행·jpackage 배포·로컬 프리뷰는 Windows 전용이다.

### 1.2 목적
사용자 한 명이 **개인 서버 한 대**에 올려 두고, Tailscale로 연결된 자기 기기(PC·모바일)에서 GitHub 이슈 수정 에이전트·리서치·루틴을 쓰고, Telegram으로 알림을 받고 명령을 보낼 수 있게 한다.

### 1.3 비목적 (Non-Goals)
- 다중 사용자, 계정·역할 관리, 공개 인터넷 노출
- GitLab 지원 유지, 메신저 방 수집·요약·대리 응답
- Slack 등 Telegram 외 메신저
- 1.x 설치와의 호환(설정·DB·실행 방식)
- 서버를 조작하는 기능(OI-01)

## 2. 범위

### 2.1 Phase 구분
| Phase | 범위 | 끝났을 때 상태 |
|---|---|---|
| 1 | Linux 기동, Tailscale 한정 접근 제어, 서버 실행 구성 | 지금 기능 그대로 서버에 올려 Tailscale 기기에서 쓸 수 있다 |
| 2 | 사내 전용 기능과 Windows 전용 요소 제거, 메신저를 "알림 + 명령 수신"으로 축소 | 수집 없이 명령·답변을 받는 경로가 있고, 쓰지 않는 코드·테이블·화면이 없다 |
| 3 | GitHub 연동(GitLab 교체) | GitHub 이슈가 Draft PR까지 간다 |
| 4 | Telegram 어댑터 | 봇과의 1:1 대화로 알림을 받고 명령을 보낸다 |
| 5 | 화면 SPA 전환(모바일 사용 포함) | 모든 화면이 SPA이고 390px에서 쓸 수 있다 |

순서는 사용자와 합의한 안을 유지한다. 근거: 1단계는 기존 동작을 바꾸지 않아 위험이 가장 작고 서버 환경 문제(OI-06·07)를 일찍 드러낸다. 제거(2)를 연동 교체(3·4)보다 먼저 해야 교체 대상 코드가 줄고 새 수신 경로 위에 Telegram을 얹을 수 있다. 단, 2단계 안에서는 **수신 경로 신설(T-006)을 제거(T-007)보다 먼저** 한다.

### 2.2 Out of Scope
- 서버의 기존 서비스 정리(사용자가 따로 한다)
- 서버 제어 기능(OI-01)
- 로컬 프리뷰를 대체할 일반 화면 검증 기능(OI-04 결정 2026-11-25: 프리뷰 삭제, 대체 계획 없음)

## 3. 용어 정의

| 용어 | 정의 |
|---|---|
| 자기 대화 | 사용자와 봇의 1:1 대화. 1.x의 "자기방". Telegram에서는 봇과의 개인 대화 |
| 명령 | 자기 대화로 보내는 지시. `이슈 …`, `질문 …`. 2.0부터 접두어 `@AI`가 필요 없다 |
| 확인 대기 답변 | 이슈 세션이 설계 확인(DESIGN_WAIT)·리뷰 확인(REVIEW_WAIT)에서 기다리는 사용자 응답. `진행`·`중단`·`피드백: …` 등 |
| 알림 | 플랫폼이 스스로 보내는 안내. 알림함에 남고, 유형이 켜져 있으면 자기 대화로도 간다 |
| 대상 저장소 | 이슈 에이전트·리서치가 다루는 GitHub 저장소. 표기 `owner/repo`, 이슈는 `owner/repo#n` |
| tailnet | 사용자의 Tailscale 네트워크 |
| 신뢰 Origin | 상태 변경 요청을 받아들이는 브라우저 출처 목록(루프백 + 설정으로 추가한 주소) |

## 4. 기능 요구사항 (FR)

**ID 규칙**: 백 단위 영역 안에서 최대 번호 + 1. 폐기 ID는 재사용하지 않는다.

### 4.1 FR-1xx · 서버 실행과 접근 (Phase 1)

| ID | 요구사항 | 우선순위 | Phase |
|---|---|---|---|
| FR-101 | Ubuntu 24.04 x86_64에서 JDK 17 이상(서버는 21)으로 기동한다 | Must | 1 |
| FR-102 | systemd 아래에서 감시·재시작·종료 규약이 동작한다 | Must | 1 |
| FR-103 | Tailscale 내부 기기(모바일 포함)에서 HTTPS로 화면을 연다 | Must | 1 |
| FR-104 | 상태를 바꾸는 모든 API는 신뢰 Origin의 요청만 받는다 | Must | 1 |
| ~~FR-105~~ | (폐기: tailnet에 개인 기기만 있어 쓰지 않는다 — OI-05, 2026-11-24) Tailscale 신원 확인 | — | — |
| FR-106 | 설치 점검(Doctor)이 Linux 서버의 준비 상태를 알려 준다 | Should | 1 |

**FR-101 인수조건**
- 일반 계정으로 `java -jar dev-agent.jar`를 실행하면, 시스템은 `GET /api/system/status`에 200으로 응답해야 한다.
- 그래픽 환경이 없는 동안, 시스템은 트레이·자동 실행 등록을 시도하지 않고 기동해야 한다.
- 로컬 프리뷰가 꺼져 있는 동안, 시스템은 프리뷰 도구(`tools/`)가 없어도 기동하고 에이전트 실행에서 오류를 내지 않아야 한다.
- 에이전트 실행 전에 심(`preview`·`jscheck`·`jspcheck`·`mvn`)을 쓰는 동작은 Linux에서 실패하지 않아야 한다(쓰지 않거나, 실행 권한이 있는 스크립트로 쓴다).

**FR-102 인수조건**
- systemd 서비스로 떠 있는 동안, `GET /api/system/status`의 실행 방식은 `systemd`여야 하고 화면의 재시작 버튼이 보여야 한다.
- `POST /api/system/restart`가 호출되면, 시스템은 종료 코드 10으로 끝나고 systemd가 다시 띄워야 한다.
- `POST /api/system/shutdown`이 호출되면, 시스템은 종료 코드 0으로 끝나고 systemd는 다시 띄우지 않아야 한다.
- 서버가 부팅되면, 서비스는 DB가 준비된 뒤 자동으로 떠야 한다.
- systemd 아래에서(로그인 셸 PATH 없음), 시스템은 Claude CLI·git·검증 명령(gradle 등)을 찾아 실행해야 한다(unit에 PATH·`JAVA_HOME` 명시).

**FR-103 인수조건**
- 시스템은 `127.0.0.1`에만 바인드해야 한다(다른 주소에 바인드하는 설정을 제공하지 않는다).
- tailnet 기기가 `https://<서버 MagicDNS 이름>:8443/`을 열면, 화면이 뜨고 실시간 로그(SSE)와 파일 올리기(리서치 첨부)가 동작해야 한다.
- tailnet 밖에서는 접근할 수 없어야 한다.

**FR-104 인수조건**
- `GET`·`HEAD`·`OPTIONS`가 아닌 `/api/**` 요청에 `Origin` 헤더가 있고 그 값이 신뢰 Origin이 아니면, 시스템은 403으로 거부하고 아무것도 바꾸지 않아야 한다.
- `Origin` 헤더가 없는 요청(curl 등 로컬 도구)은 지금처럼 통과해야 한다.
- 신뢰 Origin은 루프백(`http://127.0.0.1:<port>`, `http://localhost:<port>`)과 설정 `ACCESS_ALLOWED_ORIGINS`(쉼표 구분)에 적은 값이어야 한다.
- 만약 `GET`으로 상태를 바꾸는 엔드포인트가 있으면, 시스템은 그것에도 같은 확인을 적용하거나 `POST`로 바꿔야 한다.

**FR-106 인수조건**
- `GET /api/system/doctor`가 호출되면, 시스템은 Linux에서 Claude CLI·git·DB 연결의 상태와 고치는 방법 한 줄을 돌려줘야 한다. Windows 전용 항목은 Linux에서 실패로 표시하지 않아야 한다.

### 4.2 FR-2xx · 사내 전용 기능 제거와 메신저 축소 (Phase 2)

| ID | 요구사항 | 우선순위 | Phase |
|---|---|---|---|
| FR-201 | 방 수집·정기 요약·멘션 초안/자동응답을 제거한다 | Must | 2 |
| FR-202 | 사내 문서 RAG를 제거한다 (OI-02) | Must | 2 |
| FR-203 | 자기 대화로 온 명령을 수집 없이 받아 처리한다 | Must | 2 |
| FR-204 | 자기 대화로 온 확인 대기 답변을 대기 중인 이슈 세션에 전달한다 | Must | 2 |
| FR-205 | 알림 경로와 유형별 끄기를 유지한다 | Must | 2 |
| FR-206 | Windows 전용 요소(트레이·자동 실행·jpackage 배포·`.cmd` 스크립트·로컬 프리뷰)를 제거한다 (로컬 프리뷰 삭제는 OI-04 결정 2026-11-25) | Must | 2 |
| FR-207 | 제거된 기능의 화면 요소를 없앤다 | Must | 2 |
| FR-208 | 내장 운영 MCP 3종(opensearch·postgres·k3s-ops)과 `운영` 질의, 사용처가 없어지는 채팅 모델 포트를 제거한다 (OI-03) | Must | 2 |

**FR-208 인수조건**
- 시스템은 내장 운영 MCP 서버를 에이전트 실행에 붙이지 않아야 하고, 설정 `mcp.opensearch-url`·`mcp.postgres-url`·`mcp.k3s-*`·`mcp.chat.*`와 `claude.*`의 채팅(warm 세션) 설정이 남아 있지 않아야 한다.
- 사용자 정의 MCP 서버(`/api/mcp-servers`)의 등록·삭제와 에이전트 실행에의 적용은 그대로 동작해야 한다(가정: 유지 — OI-03).
- 연동 카드(`GET /api/platform`)는 남은 포트(메신저, 코딩 에이전트)만 보여 줘야 한다.

**FR-201 인수조건**
- 시스템은 사용자가 보내지 않은 메시지(다른 방, 다른 사람)를 읽거나 저장하지 않아야 한다.
- 관련 스케줄(수집·요약·멘션 폴링), 설정 키(`bot.collect`·`bot.summary`·`bot.mention`·`bot.safety`), 테이블([03 §2](./03-data-model.md#2-설계-결정))이 남아 있지 않아야 한다.

**FR-203 인수조건**
- 메신저 어댑터가 자기 대화의 새 메시지를 넘기면, 시스템은 첫 단어로 명령을 구분해 처리하고 결과를 자기 대화로 답해야 한다: `이슈 …` → 이슈 에이전트 명령, `질문 …` → 리서치 접수.
- 만약 알 수 없는 메시지이고 대기 중인 세션도 없으면, 시스템은 쓸 수 있는 명령을 한 번 안내해야 한다.
- 시스템은 자기가 보낸 메시지를 명령으로 처리하지 않아야 한다(어댑터가 넘기지 않는다 — 접두어 제외 규칙 불필요).
- 재시작 뒤에도 같은 메시지를 두 번 처리하지 않아야 한다(수신 커서 저장).

**FR-204 인수조건**
- 대기 중인 세션이 1건인 동안 `진행`·`승인`·`중단`·`diff`·`상태`·`피드백: …`이 오면, 시스템은 그 세션에 전달해야 한다.
- 대기 중인 세션이 2건 이상인 동안, 시스템은 메시지 앞에 세션 참조(`repo#n`)가 있을 때만 전달하고 없으면 안내해야 한다.
- 그 외의 글(잡담·스티커)은 답변으로 쓰지 않아야 한다.

**FR-205 인수조건**
- 알림이 생기면, 시스템은 알림함에 남기고 해당 유형이 켜져 있을 때만 자기 대화로 보내야 한다. 유형은 `issue`·`research`·`system`(요약·멘션 유형은 폐지).
- 메신저가 `none`이거나 전송이 실패해도, 시스템은 예외 없이 알림함 기록을 남겨야 한다.

**FR-206 인수조건**
- 저장소에 Windows 전용 실행 요소(`boot/Launcher`의 트레이, `boot/Autostart`, `gradle/dist.gradle`의 jpackage, `run.cmd`·`stop.cmd`·`restart.cmd`·`admin.cmd`·`list-rooms.cmd`·`install-autostart.ps1`, `preview/`·`scripts/`)가 남아 있지 않아야 한다.
- 개발 PC(Windows)에서 `gradlew.bat test bootJar`와 `java -jar` 실행은 계속 돼야 한다.

**FR-207 인수조건**
- 화면에 방 설정·최근 활동·요약·멘션 초안·사내 문서(RAG)·프리뷰 요소가 보이지 않아야 하고, 제거된 API를 부르는 요청이 없어야 한다(브라우저 콘솔 오류 0).

### 4.3 FR-3xx · GitHub 연동 (Phase 3)

| ID | 요구사항 | 우선순위 | Phase |
|---|---|---|---|
| FR-301 | 대상 저장소를 `owner/repo`로 등록·삭제한다 | Must | 3 |
| FR-302 | 대상 저장소의 열린 이슈 중 스캔 라벨이 붙은 것을 자동으로 큐에 넣는다 | Must | 3 |
| FR-303 | 이슈 처리 흐름(분석 → 설계 확인 → 수정 → 검증 → 리뷰 확인 → 푸시)을 유지한다 | Must | 3 |
| FR-304 | 작업 브랜치는 저장소 기본 브랜치에서 분기하고 `{유형}/{이슈번호}`(예 `fix/12`)로 이름 짓는다. hotfix 전용 분기와 일감번호 추출은 없다 (OI-10 결정 2026-11-25) | Must | 3 |
| FR-305 | 푸시 뒤 기본 브랜치를 대상으로 Draft PR을 만들고 이슈에 코멘트를 남긴다 | Must | 3 |
| FR-306 | 화면의 이슈 목록·이슈 등록·리서치의 저장소/브랜치 선택이 GitHub로 동작한다 | Must | 3 |
| FR-307 | 인증은 `.env`의 토큰 하나로 한다(API·git 푸시 공통) | Must | 3 |

**FR-302 인수조건**
- 스캔 주기가 되면, 시스템은 라벨(기본 `ai-fix`)이 붙은 열린 이슈를 큐에 넣되 Pull Request는 이슈로 취급하지 않아야 한다.

**FR-304 인수조건**
- 시스템은 기본 브랜치에 직접 푸시하지 않고 강제 푸시하지 않아야 한다. 같은 이름의 원격 브랜치가 있으면 지금처럼 접미사(`-ai`, `-ai-r<MMddHHmm>`)를 붙여야 한다.
- 이슈에 hotfix 라벨(`hotfix`/`긴급`)이 있거나 설계의 작업 유형이 hotfix여도, 시스템은 기준 브랜치를 저장소 기본 브랜치로 두어야 한다. `{유형}`은 작업 유형(`feature`·`fix`·`refactor`·`doc`·`hotfix`)을 그대로 쓴다.

**FR-305 인수조건**
- 푸시가 끝나면, 시스템은 `draft: true`, `base` = 기본 브랜치로 PR을 만들고 본문에 이슈 닫기 참조를 넣지 않아야 한다(사람이 확인한 뒤 닫는다 — 가정. OI-10 결정은 브랜치 규칙만 다뤘다).
- 만약 PR 생성이 실패하면, 시스템은 푸시된 브랜치를 그대로 두고 오류를 알림함과 세션 이벤트에 남겨야 한다.

**FR-307 인수조건**
- 토큰이 없거나 권한이 부족하면, 시스템은 기동은 하되 Doctor와 연동 카드에서 원인과 고치는 방법을 알려야 한다. 토큰 값은 로그·응답·화면에 싣지 않아야 한다.

### 4.4 FR-4xx · Telegram (Phase 4)

| ID | 요구사항 | 우선순위 | Phase |
|---|---|---|---|
| FR-401 | `MessengerPort`의 Telegram 구현체를 제공한다(`platform.messenger=telegram`) | Must | 4 |
| FR-402 | 허용한 대화(사용자 본인의 chat id) 하나만 상대한다 | Must | 4 |

**FR-401 인수조건**
- 어댑터가 켜져 있는 동안, 시스템은 서버에서 밖으로 나가는 연결만으로(수신 포트를 열지 않고) 새 메시지를 받아야 한다.
- `health()`는 네트워크 호출 없이 즉시 답해야 한다.

**FR-402 인수조건**
- 만약 허용하지 않은 대화에서 메시지가 오면, 시스템은 처리하지 않고 답하지도 않아야 한다.

**FR-403 인수조건**
- 메시지가 Telegram의 한 건 길이 한도를 넘으면, 시스템은 나눠 보내야 한다.

**FR-501 인수조건**

**FR-502 인수조건**
